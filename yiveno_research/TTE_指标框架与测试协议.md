# Time-to-Evidence（TTE）指标框架与测试协议

**版本：**v1.0  
**用途：**衡量用户从提出模糊的“我以前见过/保存过某个东西”需求，到拿到可验证原始证据所需的真实时间。  
**适用对象：**浏览器历史搜索、书签管理器、read-later、PKM、AI memory、个人上下文层与 Yiveno。  
**指标性质：**本框架是产品研究与实验定义，不是已测得的竞品性能排行榜。  
**Yiveno 术语：**用户输入称 **clue**（线索）；遥测事件 `clue_submitted` / `clue_refined`，见 [`docs/product/Yiveno-术语表.md`](../docs/product/Yiveno-术语表.md) §10.1。

## 1. 为什么不能只测“搜索响应时间”

普通搜索 latency 只回答“系统多快吐出文本”。但用户真正的任务是：他模糊记得某个资料存在，必须在可信来源上确认它就是自己要找的内容。一个 1 秒返回的 AI 总结，如果没有原 URL、可打开的原文、对应片段或明确来源，并不构成证据；反之，一个结果在 8 秒内给出原文高亮、保存时间和深链，对研究、写作和决策更有用。

> **TTE 的目标不是奖励最快生成答案，而是奖励最快交付用户可以自行核验的原始证据。**

## 2. 核心定义

### 2.1 计时起点与终点

| 项目                              | 定义                                                                                                                    | 记录方式                                                       |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **起点 t0**                       | 用户提交模糊检索请求的瞬间（**Yiveno：提交 clue**）。                                                                   | 屏幕录制帧时间或客户端 `clueSubmittedAt` / `clue_submitted`。  |
| **合格证据单元（Evidence Unit）** | 至少包含原始来源标识、可访问原文/已保存副本的深链、与任务相关的内容片段或明确锚点；并满足受试者或标注员的任务关联判断。 | 结果卡与原文页面截图；保存 clue/result/action 事件。           |
| **终点 tE**                       | 用户首次看见合格证据单元的瞬间。若需要打开原文确认，则记录首次原文已打开并显示匹配片段的瞬间。                          | `evidence_visible_at` 与 `source_opened_at`。                  |
| **超时 / 右删失**                 | 在预设窗口内未得到合格证据。                                                                                            | 记录为 `censored=1`，禁止用任意大数替换。建议观察窗口 180 秒。 |

### 2.2 主指标与配套指标

| 指标                                   | 公式                                                         | 回答的问题                         | 是否主 KPI            |
| -------------------------------------- | ------------------------------------------------------------ | ---------------------------------- | --------------------- |
| **TTE-V（Verified Time-to-Evidence）** | `tE − t0`，终点为用户看到可核验原文证据                      | “我多快拿到了足以相信的证据？”     | **是**                |
| **TTE-F（First Evidence）**            | 首个合格证据卡出现时间 − `t0`                                | “系统多快给出第一个可验证候选？”   | 是，诊断用            |
| **TTE-C（Confirmed Evidence）**        | 用户打开原文并确认相关的时间 − `t0`                          | “我多快完成了最终确认？”           | 是，研究/决策任务必测 |
| **Evidence Success@180**               | `180 秒内成功取得合格证据的任务数 / 总任务数`                | “能否在合理时间内完成？”           | **是**                |
| **Top-k Evidence Precision**           | 前 k 个显示证据中被判定相关的比例                            | “快是否是靠大量无关卡片堆出来的？” | 是，护栏              |
| **Evidence Completeness Score（ECS）** | 见下节，0–5 分                                               | “证据是否具备自我验证所需信息？”   | 合格门槛              |
| **Interaction Burden（IB）**           | 从 `t0` 到 `tE` 的 refine clue、筛选、滚动、打开结果等操作数 | “速度是否依赖用户做过多工作？”     | 诊断用                |
| **Wrong-path Penalty（WPP）**          | 在首次合格证据前打开的不相关结果数                           | “系统造成了多少错误追查？”         | 诊断用                |

任何 TTE 报告必须同时给出 **P50、P75、P90、Success@180、ECS 合格率和样本量 n**。禁止只报平均值，因为少数长尾失败会被平均数掩盖。

## 3. 什么算“可验证的原始证据”

### 3.1 Evidence Completeness Score（ECS，0–5）

每个候选证据单元按下表打分；**ECS ≥ 4 且任务相关**才可以停止 TTE-V 计时。对于论文、法律、财务或高风险任务，建议要求 ECS = 5。

| 分项             | 1 分的必要条件                                               | 说明                                        |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------- |
| 1. 来源身份      | 显示可识别的原始 URL、发布者或源平台。                       | 不能仅显示“AI 说”。                         |
| 2. 直接可达      | 用户可一键打开原网页或保存时副本。                           | 链接失效时，保存副本也可，但必须标示状态。  |
| 3. 内容锚点      | 显示相关原文摘录、标题、时间戳、视频时间点或文档页码。       | 让用户不必再猜为什么命中。                  |
| 4. 时间/来源语境 | 至少显示保存时间、发表时间、来源平台或用户保存行为中的一个。 | 模糊需求常含“几个月前”“在 X 上”等记忆线索。 |
| 5. 命中解释      | 显示关键词、实体、项目、相似度或用户行为等命中理由。         | 防止黑箱式“也许是它”。                      |

### 3.2 不合格的“快速答案”

以下情况不能停止 TTE 计时：只有无来源的生成式总结；只有搜索标题却不可打开原文；返回宽泛 topic cluster；列出多个候选但没有内容片段；指向需要再次手工全站搜索的首页；或“AI 记忆”声称知道答案却不揭示证据来源。

## 4. 模糊需求任务集

TTE 不能只用精确标题测试，否则会退化成 keyword lookup。建议固定使用 5 类任务、每类至少 6 个、每位受试者至少完成 10 个随机任务。任务由参与者自己的历史保存资料中生成，且在测试前至少间隔 14 天；更有代表性的队列应覆盖 30 天、90 天和 180 天的资料。

| 任务类型      | 用户提示模板                                                 | 必要线索                     | Gold Evidence 的定义             |
| ------------- | ------------------------------------------------------------ | ---------------------------- | -------------------------------- |
| 内容 + 时间   | “我三个月前存过一篇解释 `X` 和 `Y` 关系的文章，里面有 `Z`。” | 主题、时间、一个细节         | 对应 article/PDF 的原文段落。    |
| 来源 + 概念   | “我在 X/LinkedIn/某 newsletter 看到过某人关于 `X` 的观点。”  | 来源、作者/平台、概念        | 原帖、原 newsletter 或保存副本。 |
| 项目 + 关系   | “我为某项目保存过反对 `X` 的证据，可能提到 A 公司。”         | 项目、立场、实体             | 可支持该任务的具体资料与段落。   |
| 格式 + 视觉   | “我保存过一张蓝色调/某种布局的参考图，和某品牌有关。”        | 视觉、品牌、用途             | 对应图片/网页/素材。             |
| 行为 + 再访问 | “我保存但没读完/后来又打开过的那篇长文。”                    | 保存或重访行为、内容大致范围 | 具备行为记录和原文的对象。       |

每个任务应在开始前由不参与测试的研究员建立 **gold card**：目标来源 ID、可接受的替代来源、关键段落/时间点、最小 ECS、任务难度、保存距今天数。若一个模糊需求可以合理对应多个资料，应预先允许多个 gold IDs，避免把正确的替代证据错误判为失败。

## 5. 最小事件模型与计时实现

| 事件               | 必备字段                                                      | 目的                             |
| ------------------ | ------------------------------------------------------------- | -------------------------------- |
| `clue_submitted`   | session_id、task_id、clue_text（或 `cluePreview`）、timestamp | 标记 t0（提交 clue）。           |
| `result_rendered`  | rank、source_id、ECS 预估、render_timestamp                   | 分析 TTE-F 与系统 latency。      |
| `evidence_visible` | source_id、rank、ECS、reason codes、timestamp                 | 标记候选 TTE-V。                 |
| `source_opened`    | source_id、deep_link、timestamp                               | 测 TTE-C 与点击摩擦。            |
| `user_confirmed`   | source_id、yes/no/unsure、timestamp                           | 区分“显示了证据”和“用户相信了”。 |
| `clue_refined`     | 原 clue、新 clue、filter、timestamp                           | 计算 IB 与 clue refinement。     |
| `task_timeout`     | timeout_seconds、last_state                                   | 可靠处理失败和右删失。           |

建议前端记录单调递增时钟，并将客户端事件与服务端 trace ID 关联。测量 **用户体验时间** 时，t0 到 tE 包含网络和渲染；诊断工程问题时再拆为 `retrieval_compute_ms`、`first_paint_ms`、`content_open_ms`。不能把后端模型 latency 当作用户 TTE。

## 6. 统一测试流程

1. **建立个人语料。** 每位参与者导入或保存至少 100 个可用资料；资料类型与来源分布应记录。不要用完全公开、所有人都知道的网页替代个人语料。
2. **冷却与任务生成。** 对候选资料等待至少 14 天，再由研究员依据 gold card 写成**模糊 clue**（向受试者朗读）；不得使用完整标题、精确 URL 或连续原文句。
3. **盲测产品。** 在相同设备、网络、浏览器、登录状态、语料范围和观测窗口下，随机化产品顺序。受试者可像日常一样 refine clue，但不能使用外部搜索引擎或另一产品。
4. **记录屏幕和事件。** 记录 t0、每次结果显示、筛选/改写、打开来源、确认和超时；屏幕录制用于审计 ECS 和误判。
5. **双重标注。** 至少两名标注员独立判断 gold match 与 ECS；出现分歧时由第三人仲裁。报告一致性（Cohen’s κ 或百分比一致率）。
6. **输出分布。** 对每个产品和任务类别报告 P50/P75/P90、Success@180、ECS≥4 合格率、IB、WPP，以及按资料年龄/来源的分层结果。

## 7. 各类产品的 TTE 路径假设（不是性能事实）

下表只描述由公开产品能力推导出的**待测路径结构**，不是对其真实秒数的声明。真正数值必须在同一语料、同一任务、同一设备下实测。

> **竞品工作流列：** 表中 `query` / `搜索` 为行业或第三方产品惯用语；**Yiveno 用户输入称 clue**（术语表 §2）。

| 产品类别                  | 从模糊请求到证据的典型路径                                                                            | 主要潜在耗时                                  | 主要 TTE 失败模式                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------- |
| 原生浏览器历史            | query → AI/历史结果 → 打开网页                                                                        | 历史范围、设备/浏览器边界、只能覆盖启用后资料 | 找不到跨浏览器/社交收藏；只给 3 个最佳匹配；缺少保存意图。 |
| Folder/Tag 书签           | keyword/filter → folder/tag 浏览 → 打开链接                                                           | 用户自己回忆分类和手工浏览                    | 需要精确命名；标签噪声；链接失效。                         |
| 全文 archive / read-later | keyword/全文 query → 文档结果 → 原文/高亮                                                             | 正文是否已成功抓取；检索词是否出现            | 对只记得语义、视觉或项目关系的任务脆弱。                   |
| AI-native bookmark/PKM    | 自然语言 query → 语义候选或 AI answer → 资料卡/原文                                                   | reranking、上下文提取、解释呈现               | AI 只给总结无来源；语义近似导致错误但看似合理。            |
| graph/手动 PKM            | 搜索 → note/object/backlink → 来源资料                                                                | 用户是否已建立对象/链接；多跳导航             | 捕获不全；需要用户先结构化。                               |
| platform AI memory        | 自然语言问题 → 模型答案 → memory/chat/app source                                                      | 模型检索、权限、来源可见性                    | “知道但不可证”；证据分散在聊天、文件、已连接应用。         |
| browser AI / Agent        | 上下文问题 → tab/history/app 检索 → 可能的 action                                                     | 浏览器范围、外发数据、权限卡                  | 能代办但没有原始证据；用户难以审计选择。                   |
| **Yiveno（目标）**        | 模糊 clue → hybrid candidates → evidence card（原文/锚点/理由）→ 1-click confirm 或 MCP evidence pack | 解析质量、hybrid ranking、实体/时间/行为重排  | 抓取失败、候选解释弱、来源授权不足。                       |

公开资料显示，Chrome 已支持自然语言的本地 AI History Search；Raindrop Pro、Reader、mymind、Recall 等已拥有不同层级的全文或 AI 检索；平台侧 ChatGPT、Claude、Gemini 与浏览器侧 Dia/Comet 都在扩展记忆、连接器或浏览上下文。[1] [2] [3] [4] [5] [6] [7] [8] [9] 因此 **TTE 的可验证性门槛** 比“是否能回答”更能拉开差异。

## 8. Yiveno 的目标阈值

这些是产品目标，而不是基于竞品实测得出的对标值。采用 180 秒观测窗口，并将无效/无来源回答视作尚未获得证据。

| 阶段              | TTE-F P50 | TTE-V P50 | TTE-V P90 | TTE-C P75 | Success@180 | ECS≥4 | 解释                                   |
| ----------------- | --------: | --------: | --------: | --------: | ----------: | ----: | -------------------------------------- |
| Alpha（内部语料） |    ≤ 3 秒 |   ≤ 15 秒 |   ≤ 60 秒 |   ≤ 35 秒 |       ≥ 70% | ≥ 90% | 先证明系统不会又快又错。               |
| Beta（种子用户）  |    ≤ 3 秒 |   ≤ 12 秒 |   ≤ 45 秒 |   ≤ 30 秒 |       ≥ 75% | ≥ 92% | 优先处理 parser、metadata 与重排长尾。 |
| PMF 探索          |    ≤ 2 秒 |    ≤ 8 秒 |   ≤ 30 秒 |   ≤ 20 秒 |       ≥ 80% | ≥ 95% | 用于跨来源、30/90/180 日真实任务。     |

同时设定两条护栏：第一，`Top-3 Evidence Precision ≥ 0.70`；第二，`Median IB ≤ 2`。如果靠展示大量卡片、诱导多轮 refine clue 或大量误点才缩短 TTE-F，则不能视为成功。

## 9. 90 天测量落地计划

| 时间       | 工作                                                                                               | 交付物                                        | 决策门槛                                                     |
| ---------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| 第 1–2 周  | 在产品中添加事件埋点、ECS 字段、原文锚点与 `user_confirmed`；建立 30 个内部 gold tasks             | 可审计 event schema、屏幕录制模板、标注指南   | 若无法记录 source_id/anchor，就不要开始对外比较。            |
| 第 3–4 周  | 内部 6–10 人、每人 10 题的首次基准；按错误类别标注                                                 | Alpha TTE 分布和失败 taxonomy                 | 优先修复内容解析、metadata 和打开原文路径，而不是加新模型。  |
| 第 5–8 周  | 20–30 位种子用户开展 2 周 diary study；每人 10 个历史任务                                          | 分群、来源、资料年龄维度的 TTE 报告           | 若 `Success@180 < 70%`，暂缓收费测试。                       |
| 第 9–12 周 | 在明确 consent 下做同语料交叉产品测试，至少对浏览器历史、现有 bookmark/read-later、Yiveno 三类方案 | 对比 scorecard、显著性/置信区间、用户访谈摘录 | 只有 Yiveno 在至少一类高价值任务显著降低 TTE-C，才扩大分发。 |

## 11. 公开资料核验：可以比较“证据路径”，不能诚实地比较“秒数”

本研究再次检查了可公开访问的产品资料。结果是：**核心产品公开描述了检索、全文、引用或来源可访问性，但未找到采用统一个人语料、统一模糊任务与统一终点定义的公开 TTE 秒数。** 因此，下表只可用于设计对照实验和解释路径差异，不能被改写成“某产品 TTE 为 X 秒”的排行榜。

| 产品                                 | 可公开核验的证据返回能力                                                                                               | TTE 相关的可观察路径                                                                   | 是否披露可复现 TTE 秒数                              | 对 TTE 实验的含义                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Raindrop.io                          | 对已保存网页、PDF、YouTube 提供全文搜索；主页称网页/文件有备份副本，文章有 highlights 和即时预览                       | query → 全文结果 → library 内 preview/highlight 或原页面/归档副本                      | **否**                                               | 应测试其精确词、领域、内容类型和归档可用性；可作为“成熟 archive + FTS”基线。                      |
| Readwise Reader                      | 主页宣称离线全文搜索、“即使只记得一个单词”；资料可在本地优先 Web app、移动端与离线环境阅读；MCP 可让 AI 从完整文档回答 | query / Ghostreader → document → highlight/文档正文；或 Agent → grounded answer → 文档 | **否**；“blazingly fast”属于营销形容，不可当计时数据 | 应分开测 keyword recall、highlight/正文确认、MCP evidence 到达三条路径。                          |
| Recall                               | 官方称保存全内容，并能在用户库聊天时提供可在原文段落验证的 citations；语义搜索、自动分类和 library chat 都已公开描述   | natural-language query → grounded chat/citation 或 semantic result → 原文 passage      | **否**                                               | 对其测量必须把“答案出现”与“citation/原文 passage 已可见”拆开，后者才是 TTE-V 终点。               |
| Chrome AI History                    | 官方说明可用自然语言找访问过的网页，启用后本地保存 title、URL 和内容；最佳匹配最多 3 个                                | detailed query → best history match → 打开网页                                         | **否**                                               | 应将其作为单浏览器、已启用历史范围内的强基线，不可用来代表跨来源个人资料检索。                    |
| ChatGPT / Claude / Gemini 等平台记忆 | 都已公开 memory、chat/history search、connected apps 或个人化的不同能力；部分展示 sources/citations/记忆管理           | question → model answer → source/memory/chat/app record                                | **否**                                               | 必须测“有回答”与“用户能打开合格原始证据”之间的差距；平台 memory 不能自动等同 evidence retrieval。 |

**方法结论。** 真正的对比需要受试者在各产品中拥有相同或等价的个人资料库，而公开网站通常不提供该条件。因此，可靠做法不是从营销页面推导秒数，而是以本协议的 gold card、同语料盲测与屏幕/事件审计生成基准。这个限制本身是 Yiveno 的产品机会：如果 Yiveno 从事件、锚点与来源级解释出发，就能把 TTE 做成产品内可观测、可优化、也可向用户说明的质量指标。
