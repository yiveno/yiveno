# Yiveno 任务级模型路由方案（2026-10）

> **本方案 = 工程演进计划。** Phase 0–1 已落地（`taskKind` + 同模路由插座）；**未配分档 env 时生产行为与今日一致**；真分模须触发表 + Normative。  
> **一句话：** 继续「职责拆分 + 统一契约」；按任务选模型/超时/配额权重——**不做**多 Agent 会商集群。

---

## 0. 契约（已与维护者对齐）

| #   | 原则                  | 含义                                                       |
| --- | --------------------- | ---------------------------------------------------------- |
| 1   | **路由 ≠ Agent 集群** | 禁止 Planner/Critic 互调、禁止模型互传未校验自由文本当事实 |
| 2   | **服从 ADR-010**      | 理解层**默认单次** NLU；条件 Stage 2 仅门禁触发            |
| 3   | **服从 ADR-004**      | LLM 只出提议；Zod/门禁 → 确定性 Filter / 写库              |
| 4   | **不抢 §5.9**         | 本方案不得以「换模型/加路由」冒充召回质量达标              |
| 5   | **数据驱动再分模**    | 无分任务基线指标前，**保持**全任务 `deepseek-v4-flash`     |
| 6   | **对外不叙事**        | 官网/商店禁止「多模型 Agent / AI-powered 架构」主卖点      |

## 1. 现状（FACT）

```text
扩展：按职责拼不同 prompt（NLU / Framing / Follow-up / Narrow polish）
  → 同一 LlmChatCompleter
  → POST /api/ai/hosted/complete（登录桶）或 clue/complete（开发）
       → AiChatProvider（默认 DeepSeek）
       → 模型 = AI_HOSTED_MODEL || deepseek-v4-flash（全任务同一）

旁路：
  POST /api/ai/enrichment/complete     → 同 chat provider
  POST /api/ai/gs-clue-samples/complete → 同 chat provider
  POST /api/ai/embed                   → Workers AI bge-m3（非对话）
```

| 已具备                              | 缺口                                                 |
| ----------------------------------- | ---------------------------------------------------- |
| 职责已分（6 类 chat 用法 + 1 向量） | 请求**无**稳定 `taskKind`；服务端无法按任务选型/归因 |
| 统一 Zod / 降级规则                 | 无分任务 P95 / schema 合法率 / 成本基线              |
| ADR-010 已拒「默认多跳理解」        | 配额桶把 NLU 与浅 NLG 混计，难以优化                 |

## 2. 目标架构

### 2.1 目标拓扑

```text
调用方声明 taskKind（闭集）
  → Worker：解析 task 配置（model / maxTokens / timeoutMs / 配额权重）
  → 同一 AiChatProvider.complete（可换 model 字符串）
  → 返回文本
  → 既有 Zod / fold / merge 门禁（不变）
  → 确定性执行（不变）
```

**禁止拓扑：**

```text
❌ Agent-A → Agent-B → Agent-C 会商
❌ 模型输出直接当下一跳「工具参数」且无 Zod
❌ 为多语再挂「语言专家 Agent」冒充通解
```

### 2.2 与 ADR-010 的关系

| ADR-010          | 本方案                                                     |
| ---------------- | ---------------------------------------------------------- |
| Stage 1 单次 NLU | 仍单次；仅允许 NLU **换更稳模型**（若数据证明值得）        |
| Stage 2 条件二次 | 仍门禁触发；可选用同档或指定「修复」模型，**不计默认路径** |
| NLG 旁路         | 可单独选便宜/快模型；**不得**改写检索约束                  |

## 3. 任务闭集（taskKind）

服务端与客户端共用同一闭集；未知 kind → 拒绝或回退 `nlu` 配置（实现时二选一，须写进 API 契约）。

| taskKind        | 职责                 | 延迟敏感             | 质量敏感         | 建议档（待基线后拍板）      | 配额                      |
| --------------- | -------------------- | -------------------- | ---------------- | --------------------------- | ------------------------- |
| `nlu`           | clue → 结构化槽位    | **高**（主路径墙钟） | **最高**         | **quality**（可与现网同模） | hosted 主桶；权重 1.0     |
| `framing_nlg`   | 结果 Framing 润色    | 中                   | 中（可降级模板） | **fast**                    | 同桶；权重 1.0（P2 可调） |
| `follow_up_nlg` | need_a_clue 追问     | 中                   | 中               | **fast**                    | 同桶                      |
| `narrow_polish` | composer 举例润色    | 低                   | 低（fold 门禁）  | **fast** / 最小 tokens      | 同桶                      |
| `enrichment`    | Capture 异步提议     | 低（异步）           | 中               | **balanced**                | enrichment 路径（现有）   |
| `gs_samples`    | Getting Started 样句 | 低                   | 低（可模板回退） | **fast**                    | GS 路径（现有）           |

**embedding** 不进本表（向量 API，非 chat 路由）。

**档位含义（配置层，非厂商名）：**

| 档         | 意图              | 现网默认映射（P0）                              |
| ---------- | ----------------- | ----------------------------------------------- |
| `quality`  | schema 稳、槽位准 | `deepseek-v4-flash`（或日后更强 DeepSeek 型号） |
| `balanced` | 质量/成本折中     | 同 flash                                        |
| `fast`     | 短输出、低超时    | 同 flash（P1 起才考虑拆型号）                   |

> P0 **故意**三档同模：先把 `taskKind` + 观测打通，再谈换模。避免「未测先分」。

## 4. 分期落地

### Phase 0 · 契约与观测（必做 · 低风险）

**目标：** 能回答「每种任务各多少次、多慢、多贵、多常降级」——仍单模型。

| 项   | 动作                                                                                                                       | 验收               |
| ---- | -------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| P0-1 | API：`hosted/complete`（及开发 `clue/complete` 若仍用）请求体增加可选 `taskKind`（Zod 闭集）；缺省 = `nlu`（兼容旧客户端） | Worker 单测 + 类型 |
| P0-2 | 扩展：NLU / Framing / Follow-up / Narrow 调用处传入对应 kind                                                               | 真机 log 可见      |
| P0-3 | Worker 日志：`taskKind` + `model` + `latencyMs` + `ok                                                                      | timeout            | quota | provider_error` + token（若有） | 抽查日志字段齐全 |
| P0-4 | 文档：本方案 status 保持 proposed；`ENVIRONMENT.md` 记可选 env 预留（先不启用分模）                                        | 无行为分叉         |

**不做：** 换默认模型、拆配额桶、对外宣传。

**预估工期：** 小（1–2 个专注窗口）。

---

### Phase 1 · 服务端任务配置表（仍可同模）

**目标：** 配置驱动超时 / `maxTokens`，为分模留插座。

```text
// 概念形状（落地时放 worker/src/config/，非客户端可改）
TaskRouteConfig = {
  taskKind → {
    modelEnvKey?: string   // 如 AI_HOSTED_MODEL_NLU；空则 AI_HOSTED_MODEL
    maxTokens: number
    // 超时：优先扩展 AbortSignal；服务端可记建议值供观测对齐
  }
}
```

| 项   | 动作                                                                                  | 验收                                       |
| ---- | ------------------------------------------------------------------------------------- | ------------------------------------------ |
| P1-1 | `resolveHostedModelForTask(env, taskKind)`；未配分档 env → 回退全局 `AI_HOSTED_MODEL` | 单测：未配 = 全同；配了 NLU 覆盖只影响 nlu |
| P1-2 | 按 task 钳制 `maxTokens`（NLG/polish 更小）                                           | 费用与超时有上限                           |
| P1-3 | Settings 配额展示仍可只显示总量；内部 log 已分 kind                                   | UI 不复杂化                                |

**触发进入 Phase 2：** 连续 ≥2 周（或约定样本量）有分任务基线，且满足 §5 任一「分模触发」。

---

### Phase 2 · 有条件分模（仅数据触发）

**仅当**下列之一成立，才改 env / 文档启用分模（**先改 Normative 一句再改生产默认**）：

| 触发 ID | 条件（建议阈值，维护者可改数字）                                          | 动作                                               |
| ------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| T-NLU   | `nlu` Zod 失败率或规则降级率显著高于可接受线，且 prompt/schema 已调仍不足 | `quality` 换更稳型号（同厂商优先）                 |
| T-LAT   | 主路径 P95（含 NLU）超产品可感预算，且 NLG 占比拖累明显                   | `framing`/`follow_up`/`narrow` → `fast` 更小更快模 |
| T-COST  | hosted 月费用或 Pro 配额压力主要来自浅 NLG                                | 同上；或 NLG 权重 / 日盖微调（须产品同意）         |
| T-ASYNC | enrichment 与主路径抢同一限流导致 Capture 积压                            | enrichment 独立 model/队列优先级（仍异步）         |

**硬闸：**

- 分模后：NLU **金标 / parse-gold 或既有 must 相关面**不得静默退步。
- Framing/Follow-up 失败 → **必须**仍降级规则模板（现状保留）。
- **禁止**为分模引入第二支付/第二数据平面。

### Phase 3 · 可选增强（默认不做）

| 项                     | 说明                                | 触发                          |
| ---------------------- | ----------------------------------- | ----------------------------- |

## 5. 指标与验收（分计）

### 5.1 基线（Phase 0–1 必采）

| 指标                                 | 维度                         | 用途                   |
| ------------------------------------ | ---------------------------- | ---------------------- |
| 调用次数                             | taskKind × tier              | 配额结构               |
| 成功 / 超时 / 429 / 5xx              | taskKind                     | 稳定性                 |
| 延迟 P50/P95                         | taskKind                     | 是否拆 fast            |
| NLU：Zod 通过率、`rules_fallback` 率 | —                            | 是否换 quality         |
| NLG：门禁失败→模板降级率             | framing / follow_up / narrow | 可接受残差             |
| 与 §5.9 / must                       | **分计**                     | 禁止用路由指标冒充 TTE |

### 5.2 完成定义（整案）

- Phase 0–1 合入且观测可读 → **方案工程底座完成**。
- Phase 2 至少一次「有触发才分模」或书面记录「观察期无触发、保持单模」→ **方案运营闭环完成**。
- **不要求**上 Agent、不要求多厂商。

## 6. 实现要点（改码时照此）

### 6.1 Worker

1. `AIHostedCompleteRequest` 增 `taskKind`（可选，默认 `nlu`）。
2. `resolveHostedModel(env)` → `resolveHostedModelForTask(env, taskKind)`。
3. 日志字段标准化（中文业务 log + 结构化字段）。
4. **不要**让客户端传任意 `model` 字符串（防刷费用）；模型只由服务端 task 配置决定。

### 6.2 Extension

1. `LlmChatCompleter` 签名演进为可带 `taskKind`（或包装 `completeForTask(kind, messages)`），避免各处魔法字符串。
2. 调用映射：

| 调用点                                    | taskKind                                                            |
| ----------------------------------------- | ------------------------------------------------------------------- |
| `parseRecallClueWithLlm`                  | `nlu`                                                               |
| `complete-recall-framing-nlg`             | `framing_nlg`                                                       |
| `complete-recall-follow-up`               | `follow_up_nlg`                                                     |
| `complete-composer-narrow-example-polish` | `narrow_polish`                                                     |
| enrichment / GS                           | 走既有专用路由；若日后合并 hosted，再标 `enrichment` / `gs_samples` |

### 6.3 配置（env 预留，Phase 1+）

| 变量                         | 含义                                 |
| ---------------------------- | ------------------------------------ |
| `AI_HOSTED_MODEL`            | 全局默认（现网 `deepseek-v4-flash`） |
| `AI_HOSTED_MODEL_NLU`        | 可选覆盖                             |
| `AI_HOSTED_MODEL_NLG`        | 可选覆盖 framing/follow_up/narrow    |
| `AI_HOSTED_MODEL_ENRICHMENT` | 可选（若 enrichment 改走可配置层）   |

未设置覆盖 → 行为与今日完全一致。

### 6.4 文档同步（Phase 2 真分模时必做）

- 产品文档：一句「服务端可按任务选择模型；默认仍单厂商；理解默认单次」。
- 可选短 ADR：「任务级路由，非 Agent 集群」——接受后链到 ADR-010。
- `ENVIRONMENT.md` / 隐私披露若点名模型族，保持与代码一致。

## 7. 风险与缓解

| 风险                         | 缓解                                             |
| ---------------------------- | ------------------------------------------------ |
| 未测先分模 → 质量漂移        | Phase 0–1 强制同模；Phase 2 门槛表               |
| 客户端伪造 taskKind 刷便宜档 | 模型不由客户端选；kind 只影响服务端配置          |
| 观测噪声                     | kind 缺省 `nlu` 会污染统计 → 扩展尽快传齐        |
| 范围膨胀成 Agent             | 契约 §0；PR 拒绝多 Agent 编排                    |
| 抢 §5.9 焦点                 | CURRENT 不把本方案列为主线，除非维护者改 CURRENT |

---

## 8. 明确不做（本方案范围外）

- 多 Agent 会商 / 工具轨迹对用户展示
- 默认双跳/三跳 NLU 流水线
- 内容别名灰名单「补」多模理解
- 为日韩东南亚预挂语言 Agent
- 现在就引入第二 chat 厂商（仅保留 adapter 插座）
- 用路由替代 prompt/schema/闭集槽位改进

## 9. 建议执行顺序（维护者可裁剪）

1. **确认本方案**（proposed → accepted，或批「先做 Phase 0–1」）。
2. **Phase 0**：`taskKind` + 日志（行为对齐今日）。
3. **Phase 1**：服务端 task 配置表 + maxTokens 分档（仍同模）。
4. **跑基线** ≥ 约定周期；对照 §5 触发表。
5. **有触发再 Phase 2**；无触发则保持单模，方案仍算成功（底座在、成本未涨）。
