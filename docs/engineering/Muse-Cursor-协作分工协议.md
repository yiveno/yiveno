# Muse × Cursor 协作分工协议

> **定位**：本协议定义外部协作 Agent **Muse** 与 IDE 工具 **Cursor** 在 Yiveno 开发中的分工、交接与审查关系。
> 它**不是**项目规则：Yiveno 硬规则的单一权威仍是 `.cursor/rules/project.mdc`，术语以 `docs/product/Yiveno-术语表.md` 为准；本协议只规定「谁做什么、如何交接、谁验收」。
> 与 `AGENTS.md` / ADR-013 的关系：Muse 不是 IDE 入口，不新增 IDE 启动文件（ADR-013 §7 适用于 IDE 工具）；Muse 对本仓的写入只走分支 + PR，由维护者合并。

## 1. 分工维度

分工不按工具能力强弱划分，按三个结构性维度划分：

| 维度 | Cursor（IDE 内） | Muse（IDE 外） |
|---|---|---|
| 时间尺度 | 会话内：分钟到小时，跟随维护者的编辑活动 | 跨天跨周：后台监控、定时检查、长期决策记忆 |
| 上下文范围 | 当前仓库的编辑状态：打开的文件、未提交改动、光标位置 | 跨源：Org 三仓 + 邮件/日历 + 研究资料 + 历史审查结论 |
| 角色本质 | 生成方：写代码、重构、试错，速度优先 | 规划与验收方：定规格、查证据、做独立审查，正确性优先 |

## 2. 标准流水线

每个非琐碎任务默认走以下五步：

1. **规格（Muse）**：动手前写成可验收的规格，复用 `docs/product/AGENT-TASK-BRIEF.template.md`：问题边界、契约、涉及文件、验收命令、对评测的影响。维护者确认后才进入实现。
2. **实现（Cursor）**：维护者在编辑器内结对完成，受 `.cursor/rules/` 约束。
3. **确定性门禁（CI）**：`ci.yml` 的 typecheck / lint / i18n / doc:check / knip / `test:run` + 显性 `test:must`；真实模型评测走 `recall-real-eval.yml`（workflow_dispatch），按其文件头所列时机手动触发。
4. **独立审查（Muse）**：实现完成后，Muse 以只读方式对照规格核查提交与相关文件，结论分级为「已修复 / 部分修复 / 未修复」，每条结论必须落到具体文件与代码证据；未读代码不下结论。
5. **运营与外围（Muse）**：域名/SSL、支付、账号安全的日常监控，上架文案、竞品与技术研究、英文表达——所有不在编辑器内的工作。

## 3. 三个协作接口

- **规格交接**：Muse 的输出必须是可直接执行的规格（含文件路径、契约、验收命令），不是散文建议；Cursor 的产出必须是以提交 / PR 为单位、可逐项核对的变更，不是口头「已完成」。
- **审查回路**：生成方不给自己的产出验收；审查方不在未读代码时下结论。任何一方的「应该没问题」都不构成验收证据。
- **沉淀回路**：审查中发现的重复性问题必须回写，而不是停留在对话里——可跨仓复用的进 `yiveno/agent-rules`（L0），可自动拦截的进 eval 用例 / CI 门禁，属于架构取舍的补 ADR。

## 4. 硬边界

- Muse 未经维护者明确批准不写入本仓；批准后也只走分支 + PR，不直推 `main`。
- 高风险区强制走完第 4 步独立审查才合并：同步链（memory-cloud-sync / account-sync）、IndexedDB schema 迁移、支付与账单（Dodo webhook）。
- 机密不入仓：密钥、Token 只走平台 Secrets，不进文档与提交记录。

## 5. 维护

- 本协议的变更走 PR；与 `project.mdc` 冲突时以 `project.mdc` 为准。
- 分工失效信号：审查长期零发现（审查流于形式），或同一类问题重复出现 ≥2 次仍未沉淀到规则 / 评测。三者出现其一，应复盘本协议是否仍被执行。
