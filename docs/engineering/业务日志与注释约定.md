# 业务日志与注释约定

新增或修改业务逻辑时，必须同时满足：

1. **中文注释 / JSDoc**：写清意图、边界、失败降级；专有名词可保留英文。
2. **关键步骤日志**：开始 → 分支决策 → 成功/失败原因；失败不可静默吞掉。

权威摘要见根目录 [`AGENTS.md`](../AGENTS.md)「代码约定 · 业务可观测性」，以及 [`.cursor/rules/project.mdc`](../.cursor/rules/project.mdc)。

## 字符串联合 / 字典字面量（硬约定）

业务侧的 `type Foo = 'a' | 'b'`、`z.enum([...])`、以及同类「封闭字面量集合」，**每个成员都必须有中文释义**。仅靠英文 slug / errorCode 不够可读。

**写法（推荐）：** JSDoc 总述 + 每个成员行尾 `// 中文`

```typescript
/**
 * 网关结论。
 * - reject_noise：硬噪音，不继续理解 / 扫库
 * - proceed：放行，交给门禁
 */
export type ClueProcessingDisposition =
  | 'reject_noise' // 拒绝：判定为噪音
  | 'proceed' // 放行：继续处理

export const RecallClueConfidenceSchema = z.enum([
  'high', // 高：多槽位齐全
  'medium', // 中：部分约束
  'low' // 低：仅弱信号
])
```

**范围：**

- ✅ 领域状态、outcome、门禁/网关结果、置信度、对象类型、行为提示、Capture 入口、errorCode、订阅/支付状态等
- ❌ 生成物 / 第三方类型定义（如 `worker-configuration.d.ts`）不必改
- ❌ 单成员且紧邻已有完整中文 JSDoc 说明的可只保留总述，但仍建议行尾补一句

新增此类类型时同步遵守；改旧代码碰到未注释成员应顺手补齐。

## 扩展（frontend）

| 能力                | 路径                                              |
| ------------------- | ------------------------------------------------- |
| 统一开始/完成/失败  | `frontend/src/infrastructure/logging/flow-log.ts` |
| 底层 logger         | `frontend/src/infrastructure/logging/logger.ts`   |
| Recall 流水线 trace | `createRecallFlowTrace()` → scope `RecallFlow`    |

常用 scope（SW 控制台过滤 `Yiveno:`）：

- `Msg` — background 消息分发
- `Capture` / `Memory` / `Import` / `Settings` / `Identity`
- `Recall` / `RecallFlow` / `ClueLlm`
- `Omnibox` / `ContextMenu` / `ChromeBookmarkSync` / `ChromeBookmarkImport`

## Backend（Worker）

线索代理等业务 handler 应打结构化 `info` / `logError`（见 `backend/src/utils/logger.ts`），至少包含：拒绝原因、配额、耗时、模型用量。全局请求中间件已有 request/response 日志，业务日志补「决策」而非重复打 HTTP 壳。

## 反例

- 只 `catch` 后降级、不打 warn/error
- 在 core 层直接 `import` Chrome / console（应注入 `trace`）
- 把整段选区/全文 LLM prompt 打进日志（用 preview / 长度字段）
- 字符串联合类型只有英文 slug、无逐项中文释义
