## 1. 核心思想（准确理解）

### 1.1 从反馈循环借到的，是系统思想，不是仿生皮肤

人脑可抽象为：已有结构 + 持续接收信息 + 根据反馈更新**认知**与**处理方式**。简化模型：

```text
M(t+1) = U(M(t), X(t), F(t))
```

- `M`：当前策略 / 参数 / 认知状态
- `X`：新信息（clue、库内容、上下文）
- `F`：结果后的反馈（找到/没找到、延迟、明确确认等）
- `U`：更新机制

**值得借鉴的：** 当前状态影响处理；处理与反馈又改变未来处理。  
**不值得照搬的：** 把大脑机械模拟成软件、默认在线改代码、或默认系统可改产品目标。

大脑也会从错误反馈中学坏。**持续学习 ≠ 持续进步**——必须检验反馈质量、识别偏差、保留纠错与回退。

### 1.2 与传统开发模式的核心区别

|              | 传统（开发者驱动迭代）    | 环境反馈驱动（本原则）                   |
| ------------ | ------------------------- | ---------------------------------------- |
| 改进由谁发起 | 开发者预测问题 → 改码发版 | 真实使用产生证据 → 在边界内调整手段      |
| 开发者重心   | 穷举场景与规则            | 建观测、归因、评估、约束与高杠杆机制     |
| 成功定义     | 版本功能更全              | 用户更快、更可靠找到自己真正想找的东西   |
| 反馈角色     | 事后建议下一次改什么      | 学习输入（须解释可信度，非直接优化目标） |

**开发者不会消失。** 早期仍大量人工观察与修复；随证据与机制成熟，把**风险可控、可验证**的改进交给系统。最终追求的不是无开发者的软件，而是**不要求开发者预先知道所有正确答案**的软件。

### 1.3 与「命题先验」的关系（必须同向，禁止误读）

产品文档 §0.1.0：**自然语言 ↔ 用户内容能否建起关系**，须用 eval / 金标先验验死；**不得**用「先上线看市场」替代命题验收。

本原则**不推翻**命题先验：

| 反馈类型                                 | 回答什么           | 能否替代命题验收                             |
| ---------------------------------------- | ------------------ | -------------------------------------------- |
| 市场/增长反馈（DAU、付费）               | Capture 意愿、渠道 | **否**                                       |
| 体验捷径（放弃率↓、点击↑）               | 短期交互           | **否**（可监控，不可冒充 §5.9）              |
| 检索质量证据（Outcome、TTE、gold、must） | 是否找得更快更准   | **否替代先验**；在命题成立后驱动**手段**适应 |

一句话：**先验验命题；反馈改进手段；目标与隐私不交给短期指标。**

## 2. 必须坚持的原则（工程子集意图）

使命 / 五问 / 四边界见 [`Yiveno-双线程发展原则.md`](./Yiveno-双线程发展原则.md)；短锚 §0.1.2 / ADR-016。下文仅展开**手段适应**相关约束。

### 2.1 环境提供证据，不自动决定正确方向

用户打开、改 clue、dismiss、出口 Found、延迟等均可作输入。但：

- 点击 ≠ 问题解决
- 未点击 ≠ 无关
- 高频功能 ≠ 最大价值
- 短期交互 ↑ ≠ 长期满意度 ↑
- 一次未找 ≠ 排序错（也可能未存、候选漏、clue 不足）

系统须**解释反馈**，不能把反馈数值化后直接优化。优化什么、何为不可接受、如何量长期价值——由产品原则规定。

### 2.2 结果是解释用证据，不是行为正确的证明

禁止「因为结果发生了，所以导致它的全部行为都正确」。须尽量区分：影响因素 vs 共现；信息缺失；系统失败 vs 数据/输入限制；样本代表性。  
不得因一次成功就无限强化策略，也不得因一次失败就立即否定。

### 2.3 不仅更新知识，还改进处理方法

学习不限于加库条目或拧几个权重。在架构与安全边界内，可逐步探索策略层适应（何时关键词足够、何时值得 Hybrid、何时扩候选、何时改写 clue、质量—延迟权衡等）。**不要求一开始全有**；按数据规模、收益、复杂度逐步验证。

### 2.4 自我调整的三层授权

| 层               | 含义                                 | 默认授权                             |
| ---------------- | ------------------------------------ | ------------------------------------ |
| **参数适应**     | 权重、阈值、候选数量等               | 可探索；须可观测、可回退、有独立评估 |
| **策略适应**     | 路径选择、预算、算法分支             | 可探索；优先离线评估再放量           |
| **目标自主改变** | 改「什么叫成功」、服务对象或价值方向 | **禁止默认授权**；仅人可改 Normative |

### 2.5 工程硬约束

1. **先可靠基础，再自适应**——不得以「未来会自我进化」放松初始质量与 §5.9。
2. **并非一切在线自动学**——缺可靠反馈时允许不调整。
3. **反馈本身要质量控制**——防样本偏差、自我强化、过拟合历史策略。
4. **隐私与本地控制优先**——不得默认上传完整私人内容与完整检索史换学习效率。
5. **可观察、可验证、可回退**——说不清依据与后果的调整，不算合格进化。

见 §5 分阶段路线。摘要：反馈质量运营 → 失败归因 → 离线策略实验 → 极窄参数自动适应 →（很后面）策略适应放量。

### 3.5 目前没有必要实现

| 项                                        | 理由                                         |
| ----------------------------------------- | -------------------------------------------- |
| 在线自动改业务代码 / 自修改 prompt 无门禁 | 不可观测、不可回退、与 ADR-004 冲突风险高    |
| 系统自行改产品目标或 KPI 定义             | ADR-016 禁止                                 |
| 为学习默认上传全文库与完整 clue 史        | 违反隐私优先；与 local-first 冲突            |
| 用大模型「反思轨迹」冒充进化              | 可见进展 Normative 禁止 CoT 秀；且不替代证据 |
| 未达 §5.9 前大上自适应排序农场            | 噪声多、归因弱、易过拟合本机习惯             |

## 4. 架构是否支持长期进化（审视结论）

### 4.1 有利现状

Recall 主链已分段（理解 → 候选/Filter → 融合排序 → 折叠/UI → Outcome）：

```text
clue → understand → candidate load / keyword filter
    → hybrid fuse / corroboration / outcome pairs / behavior
    → UI 邻域 → open / dismiss / exit → Outcome / telemetry
```

- **core 纯函数 + application 编排** 便于对单段加探针与离线 replay。
- **eval 与 storage 解耦**（关键词 eval 不读 Outcome storage）利于独立评估。
- **双轨入口**（Omnibox vs Side Panel）天然支持不同质量—延迟政策。

### 4.2 明确限制（最小改进即可，非强制重构）

1. **候选漏是最大盲区**：只从「已返回结果」学，无法发现未入池目标——需 gold / 探针 / 事后补标，而非只加排序特征。
2. **会话 Outcome 稀疏且歧义**：个人库会话量小；strong 正例少；隐式 C 通道须持续校准。
3. **无统一「适应配置」面**：权重与阈值散落常量；要参数适应须先收拢可调点与版本。
4. **不必为进化而拆 pipeline**：当前分层足够支撑「分段观测 → 离线实验 → 受控合入」；重构收益低于先补归因与评估运营。

## 5. 分阶段开发路线（R5 · 建议）

> 执行细节写入 [`Yiveno-改版计划-v1.md`](./Yiveno-改版计划-v1.md) **R5**。此处按价值 / 成本 / 风险 / 验证难度排序。  
> **前置总闸：** §5.9 种子验证与 Outcome 标签质量未稳住前，不做策略自动放量。

### Phase A · 立即值得做（高杠杆、低自主风险）

| 项                                                       | 价值                     | 成本 | 风险 | 验证             |
| -------------------------------------------------------- | ------------------------ | ---- | ---- | ---------------- |
| 维持并硬化 §7.2（strong/unknown、正例佐证、None 撤脏对） | 反馈质量                 | 中   | 低   | Label KPI + must |
| 失败 case → 可复用机制 → `recall-eval` must（禁灰名单）  | 手段改进仍人工但证据驱动 | 中   | 低   | CI must          |
| TTE/telemetry 定期导出解读（含 `pipelineTiming`）        | 观测                     | 低   | 低   | 周报级人工       |
| 真实库 eval 可读报告（维护者本机）                       | 独立评估                 | 中   | 低   | 与工厂 must 分计 |

**不做：** 自动改权重上线、自动选 Hybrid。

### Phase B · 等待更多真实使用数据后做

| 项                                                                | 前置                        | 说明                     |
| ----------------------------------------------------------------- | --------------------------- | ------------------------ |
| 失败归因标签（至少：候选漏 / 排序错 / 理解偏 / 未存 / clue 不足） | 有 gold 或可复现会话 + 导出 | 先离线标注规范，再谈自动 |
| 已知目标「是否入候选集」探针                                      | 种子金标或本机 gold 卡      | 专治盲区                 |
| 离线策略对比（keyword-only vs Hybrid vs 扩候选）                  | 同批 clue 集 + 延迟指标     | 先报告，后人工合入常量   |
| Outcome Label rate 运营门                                         | 本机/种子样本量够           | 未达标不开 C2 settled    |

### Phase C · 长期、高成本，仅当 A/B 证明收益

| 项                                                       | 条件                                             |
| -------------------------------------------------------- | ------------------------------------------------ |
| 极窄参数自动适应（带版本、回退、退化检测）               | 参数面收拢；独立评估门绿；隐私仍本机             |
| 场景策略选择器（受预算与入口约束；Omnibox 仍守 ADR-007） | 离线实验稳定增益；无整体回归                     |
| 跨用户聚合学习                                           | **默认不做**；若做须最小必要、授权、不可还原内容 |

### Phase D · 当前不值得做

- 自主改产品目标 / KPI
- 无门禁自改 prompt 或自写规则表冒充通解
- 用点击率直接 RL 优化排序
- 为「看起来像 AI 进化」堆复杂度

## 6. 独立审视：假设、误区与工程风险

### 6.1 同意且应坚持的部分

- **目标稳定、手段适应**——与 Yiveno「找东西」定位、邻域承诺一致。
- **反馈分级与 unknown**——§7.2 已走在正确路上；比盲目点击学习成熟。
- **独立评估**——`recall-eval` must / TTE 与日常行为分计，是防指标腐化的关键。
- **隐私优先**——与 local-first、最小上传一致。
- **开发者重心上移**——与当前「失败 case → 机制 → must」工作方式同构，只是把闭环写死为长期方向。

### 6.2 需警惕的误区

1. **类比过度：** 「像生命体」易滑向无限自改；本产品必须停在参数/策略层。
2. **样本稀疏：** 个人记忆召回会话少、gold 贵；自适应统计功效弱——**过早在线学习会学噪声**。
3. **因果难：** 无对照时，Outcome 对升权可能强化「已经找得到的」；候选漏仍看不见。
4. **指标替换价值：** Verified Retrieval / TTE 是好尺，仍可能被 UI 诱导或出口条滥用污染——须保持 unknown 与校准。
5. **与命题先验的话术冲突：** 对外/对内若只讲「环境驱动」，会被听成「先上线再看」——文档必须同屏强调先验。
6. **Omnibox 特殊性：** 极短延迟路径上做深度适应，容易毁掉该入口存在理由（ADR-007）。
7. **复杂度税：** 策略选择器 + 版本 + 评估门的工程成本，常高于再人工拧一轮常量；**仅当人工循环成为瓶颈再上**。

### 6.3 对「软件能否从当前反馈识别有效改进」的判断

| 问题                       | 当前判断                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 反馈能否区分相关 vs 偶然？ | **部分能**（strong Found / dismiss / absent）；大量仍为 `unknown`——诚实保留比硬贴标签重要 |
| 自适应收益是否值得复杂度？ | **现阶段多数不值得自动**；值得的是观测、归因、离线对比与 must 硬化                        |
| 谁决定目标？               | **人（Normative）**；系统最多在授权面内调手段                                             |
| 本地/隐私下如何学？        | 本机 Outcome 对、行为 soft rank、telemetry 导出；聚合学习非默认                           |

**总判：** 理念方向正确，且与仓库已有 Outcome/eval/TTE **同构**；但若把「环境反馈驱动」读成「马上自动进化」，则与稀疏反馈、候选盲区、§5.9 未达标的现实冲突。正确落地是：**先把证据与归因做成开发者的外骨骼，再把最窄、最可回退的一环交给系统。**
