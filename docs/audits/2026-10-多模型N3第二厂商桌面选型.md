## 5. 为何用现有 37 条 parse-gold 做初筛（方法 · 非成绩）

**FACT（用例规模）：** `PARSE_GOLD_CASES` = **must 29** + **stretch 8** = **37**（与用户所述一致）。

**为何值得（方法论证 · 非「候选已更强」）：**

1. **同输入、同 judge、同 L1/L2 口径** — 已有 Flash verify 快照；候选只能比「同一契约下的槽位对错与 Schema」，不能拿 Arena/LMSYS 代替。
2. **主任务正是 NLU** — 产品主检索链路上 LLM 只做 clue→槽位；37 条覆盖 must 回归面 + stretch 难例，成本可控（授权后约一轮离线，无需动 Filter/Hybrid）。
3. **失败可归因** — 已有 `classify-parse-gold-failure` / JSON 报告；可分 L1（JSON/Zod）vs L2（槽位）看是「不会出 JSON」还是「槽填错」。
4. **过筛门槛建议（RECOMMENDATION · 确认前不执行）：** 候选 L2 must **≥** Flash 27/29，且 must 回归集合可解释；stretch 作为辅证，不单独用营销基准取代。

**明确不证明：** parse-gold ≠ §5.9；≠ 生产延迟/配额；≠ 召回 Hit@k。
