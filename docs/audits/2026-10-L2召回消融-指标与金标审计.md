## 1. TLS / mint 失败定位（FACT）

| 环节                                          | 无 `NODE_EXTRA_CA_CERTS`                                          | 有 `/etc/ssl/cert.pem`（与 worker `dev` 同源） |
| --------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| Bun `fetch(SUPABASE…/auth/v1/health)`         | `unknown certificate verification error`                          | 仍可能失败（Bun fetch ≠ SDK 路径）             |
| `admin.auth.admin.listUsers` / `generateLink` | 上轮 BLOCKED：`listUsers: unknown certificate verification error` | **成功**                                       |
| `anon.verifyOtp`                              | —                                                                 | **成功**                                       |
| Worker `POST /api/ai/embed` + Bearer          | 无 token → 401                                                    | **HTTP 200** · model=`@cf/baai/bge-m3`         |

**失败点：** 本机 → Supabase Auth Admin API 的 **TLS 信任链**（mint 前置），**不是** Worker 拒绝合法 JWT，也不是鉴权被绕过。

**修复（合法、不降鉴权）：**

1. `run-retrieval-ablation-real.mjs` 默认注入 `NODE_EXTRA_CA_CERTS=/etc/ssl/cert.pem`（与 `worker/package.json` `dev` 一致）
2. mint 改为优先 `generateLink`（已有评测用户免 listUsers）；证书类错误附 TLS 提示
3. 仍经 Worker Bearer；无硬编码 token、无提交凭据

本轮：`tokenSource=supabase_admin_mint` · user=`retrieval-ablation-local@yiveno.dev`。

## 3. Yellowstone 意图 A 分环节观察（不改生产）

**case：** `ablate-yellowstone-exclude-hike-clear`  
**期望：** miss@5 · 禁止 `hikingYellowstoneExcerpt`（…311）  
**结果（FACT）：** keyword / semantic / hybrid 均 **r=1 · negFP=true**

| 环节        | 本实验实际行为（FACT）                                                                                                                                    | 观察                                                   |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1. 理解快照 | 固定 `goldParsed`：`contentTerms` 含 `yellowstone, lodging, booking, confirmation, summer, **not**, day-hike, packing, checklist`；**无**结构化「排除」槽 | 「not」被当成普通 contentTerm，不是否定算子            |
| 2. 约束传递 | ablation runner **无**否定/排除过滤；`clueEmbeddingText`≈词面拼接                                                                                         | 排除意图未变成可执行约束                               |
| 3. 候选过滤 | keyword：词面命中 hike/packing/checklist/yellowstone → 311 入池；semantic：余弦近邻仍以 311 为首                                                          | 过滤阶段**未**因「not … checklist」剔除 311            |
| 4. 最终排序 | 三策略 Top1 均为 311                                                                                                                                      | 失败在终排上表现为 negFP；根因不预设为「排序公式坏了」 |

**失败阶段定位（本实验链路）：** 优先落在 **理解快照未编码排除 + 下游无否定过滤**（环节 1→2→3），终排只是暴露结果。  
**未验证：** 生产实时 `parseRecallClue` 是否会产出更好的排除表示（本实验冻结 goldParsed，不能外推）。  
**HYPOTHESIS：** 即使 LLM 写出排除槽，若检索层无对应硬/软过滤，仍可能误报——待另案验证。
